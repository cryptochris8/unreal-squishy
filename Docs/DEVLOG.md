## 2026-06-22 — ROOT CAUSE FOUND + FIXED: dead IMC_Squishy double-processed every key press  (Claude + Chris)
- **The off-by-one was real and is now solved.** Symptom history: pop on 2 (expected 3), then on 1 (expected 2) — always one squish early, and ONLY on Chris's real input (synthetic Slate clicks always measured single-fire, which sent us chasing ghosts for many rounds).
- **Root cause:** the character's `BeginPlay → AddSquishContext` added the leftover Enhanced-Input mapping context **`IMC_Squishy`** (maps LMB **and** F → `IA_Squish`, which has **no handler** — abandoned approach). So every real LMB/F press was processed **twice**: once by the live **legacy `InputKey`** event (→ `OnSquishPressed`) and once down the Enhanced-Input path — two `OnSquishPressed` calls per press, landing far enough apart that the friend's 0.12s cooldown didn't swallow the second. Synthetic `ProcessMouseButtonDownEvent` injection only triggers the legacy path, so it could never reproduce it.
- **How we finally proved it:** dropped `JoyPerSquish` to **0.1** + an on-screen Joy readout; Chris clicked once and watched it climb `0.1→0.2→…→1.0` over **ten** clicks (one increment per click) → double-fire gone, confirmed single-fire.
- **Fix:** disconnected `BeginPlay → AddSquishContext` so `IMC_Squishy` is never added. Legacy `InputKey` LMB/F events fire on their own (independent of mapping contexts); movement/camera come from the controller's `IMC_Default`/`IMC_MouseLook`, untouched. No functionality lost (IA_Squish had no handler).
- **Restored final tuning:** `JoyPerSquish 0.34` (≈3 squishes per CLAUDE.md §2), `SquishCooldown 0.12`. Removed all debug probes (friend Joy print, character `OSP_FIRE`/`LMB_DOWN` prints). Both BPs compile clean, saved.
- **Diagnostic process (Chris's rule paid off):** 4 rounds of parallel read-only agents + live PIE coin-counter measurement narrowed it to "real-input-only double, both keys" → which uniquely implicated the shared Enhanced-Input context. [[escalate-parallel-agents-after-2-tries]]

## 2026-06-21 — ROOT CAUSE of pop-on-2: squish was area-of-effect, not single-target (live-measured + verified)  (Claude + Chris)
- **The real bug:** `BP_SquishyCharacter.OnSquishPressed` squished **every** friend within 350cm (an AoE `GetAllActorsOfClass` loop). Friends sit 250–300cm apart, so each click charged **2–3 friends at once**. Joy never decays, so a neighbor "never touched" was already partly filled from an earlier nearby click and popped in 2. (Not a literal double-click — two friends reacting per click.)
- **How we finally caught it:** added a temporary on-screen Joy readout to the friend's `Squish`; Chris saw **two `.34`s on click 1, two `.68`s on click 2** — two identical values = two distinct friends each single-fired (a real per-click double would read `0.34` then `0.68`). That killed the double-fire theory and pointed at AoE + residual charge.
- **Fix:** rewrote `OnSquishPressed` to **single-nearest-target** — loop all friends, track the closest within 350cm via `Distance(GetActorLocation(friend), GetActorLocation(self))` into member vars `NearestDist`/`NearestFriend`, then squish only that one. (Used vector `Distance`, not `GetDistanceTo`, to dodge the DSL positional→`self` trap. The DSL read-back *looks* like the distance is hoisted out of the loop, but node-level inspection confirms it's fed per-iteration by the loop's cast output — the reader just serializes shared pure chains confusingly.)
- **Verified live (Slate click injection in PIE):** placed 3 friends at 150/250/283cm; one click charged **only the 150cm nearest** to 0.34, the other two stayed 0. Arm-gate correctly ignored the focus click. Single-nearest confirmed.
- **Net:** walk up to a friend → each click charges only *it* → 0.34→0.68→1.02 → pops on the **3rd**. Neighbors untouched.
- **Process win:** 3 parallel agents (round 1) proved the friend math + input were single-fire; the instrumented Joy readout exposed the AoE; a 4th agent ran a live PIE measurement to verify the fix before bugging Chris. [[escalate-parallel-agents-after-2-tries]]
- **Tuning decision (Chris):** with single-target working, the friend still *appeared* to pop on 2 (the 3rd squish's `1.02` print coincides with the vanish). Rather than chase the off-by-one perception, set the design to a **clean intentional 2-squish**: `JoyPerSquish 0.34 → 0.5` (so 0.5 → 1.0 hits the genuine 1.0 threshold on squish 2). Verified CDO + all placed instances now read 0.5. Removed the temporary Joy `PrintString` from `BP_SquishyFriend.Squish` (re-linked SetJoy → SetSquishImpulse). To go back to 3 squishes later, set `JoyPerSquish` to ~0.34.

## 2026-06-21 — Fixed: every friend squished on every click (proximity gate root cause)  (Claude + Chris)
- **Symptom (Chris):** friends Happy-Popped after **2 clicks not 3**, the **join/focus click** counted as a squish, and **ALL squishies squished at once** regardless of distance.
- **Root cause:** in `BP_SquishyCharacter.OnSquishPressed`, the `GetDistanceTo` node was mis-wired — the **friend** (cast result) went into the **target/`self`** pin and **`OtherActor` was empty**, so it evaluated `friend.GetDistanceTo(null) = 0`. `0 <= 350` is always true → every friend in the level squished on every press (incl. the spawn focus-click, even though the nearest friend is ~450 cm away). With all 9 filling in parallel, the pop math looked like "2 clicks."
- **Fix:** rewired by **pins** (not DSL) — detached friend from `self` (now defaults to the character) and connected friend → `OtherActor`. Now `character.GetDistanceTo(friend)` is the real distance. Verified at pin level, compiled clean, removed the temp `SQUISH PRESSED` debug print, saved.
- **One fix, three symptoms gone:** only friends ≤350 cm squish · spawn join-click reaches nobody · a friend needs 3 deliberate squishes to pop.
- **⚠️ MCP/DSL gotcha (new, recorded in `MCP_NOTES.md`):** `write_graph_dsl` binds a **positional** arg to a node's **first pin = the target/`self`**, not the first *named* parameter. `(Transformation|GetDistanceTo _friend)` therefore puts the friend on `self` and leaves `OtherActor` empty — exactly this bug. For target-functions with extra params, **wire pins explicitly** or pass the param by keyword; never trust positional. (A DSL rewrite of this graph would re-break it — hence the pin-level fix.)
- **Process note (Chris's new rule):** this took too many sequential turns; should have **instrumented on try 1**. New rule saved to memory: after 2 failed tries, **launch parallel research agents**. [[escalate-parallel-agents-after-2-tries]]
